# Task: Template-based alert builder — admin creates alerts from any semantic metric

Implements spec §1.6.1 (`SEMA-Client-Screens-Spec.pdf` v1.4). Today alerts are hand-written SQL blocks inside metric YAMLs (`sql/semantic/*.yaml` → `alerts:`), consumed by `sema_core/alerts_engine.py`; the admin can only toggle/threshold them (Phase 3 Alerts area). This task makes alerts composable: **alert = metric + template type + parameters**, SQL generated by the engine from the semantic metric definition. Follow `AGENTS.md`. Run AFTER Phase 3 (touches its Alerts UI area).

## Backend — template engine

1. **Four template types** in a new `sema_core/alert_templates.py`:
   - `pct_change` — params: window (`dod`/`wow`/`mom`), direction (`drop`/`rise`), threshold_pct.
   - `absolute_threshold` — params: operator (`above`/`below`), value.
   - `anomaly` — params: n_sigma (default 2), baseline window fixed 28d.
   - `streak` — params: n_days, direction.
   **MVP scope decision (July 2026, user-approved): metric selection is LIMITED to the existing computed-metric catalog** — the same catalog Phase 3's home-config uses (revenue/orders/aov/churn_risk and whatever the computed layer already exposes daily series for). Templates evaluate over the series the app ALREADY computes (`overview.py`/`daily_brief.py`/`alerts_engine.py` layers) — do NOT build a generic SQL re-scoping engine for arbitrary certified metrics; that is explicitly V2 (documented in spec §1.4 + §1.6.1 v1.9, same dependency as the free KPI picker). Where a template needs SQL (e.g. absolute threshold on a metric with existing alert SQL), reuse the existing resolution — never re-parse or duplicate metric SQL. Everything runs under the existing read-only role + safety guards.
2. **Org alerts store** `org_alerts(id, client_id, name UNIQUE per client, metric, template, params JSON, severity, enabled, created_by, updated_at)` — org-owned, NOT in the semantic YAML (the semantic model belongs to the platform; alerts belong to the org). Limit: 12 enabled per client.
3. **Migration of existing YAML alerts.** Map each current alert to a template where expressible (`revenue_mom_drop` → pct_change/mom/drop/8, `churn_risk_count` → absolute_threshold/above/300, etc. — audit all of them across both tenants). Expressible ones become editable org_alerts rows (seeded once, YAML block then ignored by the engine); non-expressible ones stay YAML-driven, flagged `system: true` — disableable, not editable. `alerts_engine.py` evaluates both sources through one code path.
4. **API** under `/api/admin/alerts`: GET list (org + system, with metric label + template summary sentence), POST create, PATCH edit/toggle, DELETE (org alerts only), and `POST /api/admin/alerts/test` — dry-run: evaluates the candidate alert against the last 90 days and returns fire count + the dates it would have fired ("would have fired 3 times in the last 90 days"). Test-run REQUIRED before create/enable (server enforces: create only with a fresh passed test token or re-runs the test server-side). All mutations audit-logged (`alert.created`/`updated`/`toggled`/`deleted`).
5. **Guards:** metric must be in the supported catalog (server-validated); deprecated/removed-from-catalog metric later → alert auto-disabled with reason, editor shows warning (mirror the home-config deprecated-metric pattern). Data scopes apply at delivery: an alert on a blocked metric is filtered per-user like brief cards (verify the existing scope filter covers alerts; wire if not).

## Frontend — builder in the Phase 3 Alerts area

6. Existing per-alert cards stay (toggle + threshold). Add "New alert" button → inline builder (not a new screen; replaces the placeholder popover from `product_placeholders_prompt.md`): metric select (the supported catalog only) → template type as 4 radio cards with one-line descriptions → params with smart defaults per type → "Run test" button showing the dry-run result inline (green "would have fired N times" / amber "0 times — consider a tighter threshold" / red error) → Save (disabled until a test passed with current values; any param change invalidates the test).
7. Template summary rendered as a natural sentence on each card in the app language ("Revenue drops more than 8% month-over-month"), built from a shared formatter, not stored text. System alerts get a "System" tag, no edit/delete.
8. Edit = same builder pre-filled. Delete with confirm popover (`useDismiss`). 12-alert limit surfaced when hit.

## Constraints

- No new deps; RTL-safe; Hebrew/English parity (template descriptions, summary sentences, test results).
- Generated SQL must pass the same safety validation as semantic validate (single SELECT, no system catalogs); tests must include an injection attempt via params (e.g. value = `1; DROP`) rejected by parameterization — params are NEVER string-interpolated into SQL.
- Tests (`pytest`): SQL generation per template (golden queries against demo data), migration mapping (every existing YAML alert either maps or is flagged system), dry-run counts on seeded data, 12-limit, deprecated-metric auto-disable, audit events, injection rejection. Run `npm run lint`, `npm run build`.

## Accept

- [ ] Admin creates "AOV drops >10% week-over-week" from the UI without touching YAML; test shows historical fire count; alert fires through the existing alerts pipeline.
- [ ] All existing YAML alerts either became editable org alerts or are visibly "System"; both kinds evaluate through one engine path.
- [ ] Deprecated metric disables its alerts with a visible reason; scope-blocked users don't receive the alert.
- [ ] Params are parameterized (injection test passes); every mutation appears in the Audit log.
- [ ] `pytest`, lint, build pass.
